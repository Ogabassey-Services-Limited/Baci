# Canonical audit events governance

## Status and scope

This document governs the Phase 1 canonical audit ledger introduced by the
20260730000000 through 20260730000500 migrations. It is a data-handling and
release contract for the immutable audit ledger, not a grant of broader
database or support access.

The covered sources are:

- public.merchants
- public.staff_members
- public.merchant_feature_settings
- private.merchant_payment_credentials

Every source-table trigger invocation uses an exhaustive, closed-world column
classification. The merchant identity guard and sensitive configuration
trigger run for every `INSERT`, `DELETE`, and all-column `UPDATE`, so a newly
added live source column fails closed until a reviewed migration classifies it.
An implementation must not work around a classification guard by adding a raw
whole-row snapshot.

## Ledger boundary

public.audit_events is an immutable, tenant-owned event ledger. It retains
snapshots rather than foreign keys to a mutable merchant, staff, or credential
row, so source deletion cannot erase historical evidence.

| Ledger field group | Contract |
| --- | --- |
| Identity and order | id, occurred_at, database_transaction_id, merchant_id, resource_type, resource_id, and action identify one ordered event. |
| Actor and source | actor_user_id, actor_type, actor_label, and source record the trusted writer's attribution; none are client-supplied audit fields. |
| Safe change evidence | changed_fields, before_values, and after_values contain only the source-specific projections below. |
| Correlation | correlation_id and request_id are optional trusted correlation values; current Phase 1 triggers leave them null rather than accepting caller values. |
| Fixed metadata | metadata is a small object with only category, operation, reason_code, and result. Unknown keys are rejected. |
| Versioning | schema_version starts at 1 and permits only reviewed bounded versions. |

The database transaction ID is deliberately generated by PostgreSQL from the
transaction that writes the event. It is the authoritative grouping key for
multiple row events from one committed database mutation. A request ID,
correlation ID, trace header, or body field must never substitute for it or be
used to overwrite it.

The ledger limits changed_fields to 64 bounded names and each before/after
object to 64 top-level keys and 16 KiB. Those limits are guardrails, not a
reason to collapse a sensitive projection into a raw JSON blob.

## Immutable writer and trust boundary

The current reviewed AFTER-trigger wrappers call the private writer. The
writer:

- has an empty search_path and explicitly qualifies database objects;
- requires trigger execution and an opaque private writer capability;
- resolves the actor in the database rather than accepting a request field;
- has EXECUTE revoked from PUBLIC, anon, authenticated, and service_role;
- inserts into a table that has forced RLS, no direct grants for application
  roles, and an UPDATE/DELETE rejection trigger.

The private capability table, writer, and every database-owner-owned trigger
or SECURITY DEFINER function are part of the database-owner trusted computing
base. A database owner, managed-platform superuser, backup operator, or a
migration approved with equivalent ownership can alter schema, functions, or
data and is outside the tamper-resistance claim. Application users,
authenticated clients, service-role application code, and unprivileged or
application-owned SECURITY DEFINER functions are not trusted to mint the
capability or write a ledger row. Any new database-owner-owned trigger code
that can obtain the capability must receive the same security review as a
ledger writer.

This boundary must be stated in any security review. Do not describe the
ledger as tamper-proof against a database owner.

## Actor, source, and correlation definitions

| Field | Allowed values or derivation | Rule |
| --- | --- | --- |
| actor_type | user, service, system | The current writer emits user for an authenticated or transaction-local database principal and service for service-role JWT context. system is reserved for a future reviewed writer path. |
| actor_user_id | Authenticated user UUID or explicit transaction-local database principal | A human/API actor wins over a conflicting configured principal; conflicting values fail closed. Service events have no forged human UUID. |
| actor_label | authenticated_user, database_principal, or service_role in the current paths | It is a bounded presentation label, never an email address or caller-provided arbitrary text. |
| source | api, database, migration, system | Current user and service JWT writes are api; an explicit database principal is database. migration and system are reserved until a reviewed trusted emitter defines them. |
| correlation_id | Trusted UUID supplied only by a future reviewed writer integration | It links a business workflow; it is not authorization and must not contain customer or credential data. |
| request_id | Trusted UUID supplied only by a future reviewed request integration | It links an accepted request to a transaction; it is optional and not a substitute for database_transaction_id. |
| database_transaction_id | PostgreSQL current transaction ID | Generated only in the writer. All events emitted in one successful database transaction share it. |

An actor-less governed mutation fails closed. A migration or controlled repair
that intentionally uses a database principal must set the transaction-local
principal in the same transaction as the mutation. It must never persist a
principal setting for a later connection or let an HTTP body choose it.

## Event naming and metadata

Actions use lowercase dot-separated names. The Phase 1 actions are:

| Resource type | Actions |
| --- | --- |
| merchant | merchant.identity.create, merchant.identity.update, merchant.identity.delete, merchant.configuration.create, merchant.configuration.update, merchant.configuration.delete |
| staff_member | staff.access_created, staff.invited, staff.accepted, staff.role_changed, staff.permissions_changed, staff.status_changed, staff.suspended, staff.reactivated, staff.removed, staff.contact_changed, staff.access_changed |
| merchant_feature_settings | merchant.feature_settings.create, merchant.feature_settings.update, merchant.feature_settings.delete |
| merchant_payment_credential | payment_credential.create, payment_credential.update, payment_credential.delete, payment_credential.cascade_delete |

Metadata is fixed to these keys:

| Key | Meaning |
| --- | --- |
| category | Stable domain label, such as merchant_identity, staff_access, merchant_configuration, merchant_feature_settings, or payment_credential. |
| operation | The database operation: insert, update, or delete. |
| reason_code | An optional controlled reason, currently merchant_cascade for credential cascade deletion. |
| result | Reserved for a reviewed bounded outcome label. Phase 1 writers do not accept arbitrary result text. |

No other metadata key is permitted. In particular, metadata must not carry
request bodies, provider responses, headers, IP addresses, raw error messages,
customer contact values, masked values, hashes, or unreviewed nested JSON.

## Redaction rules that apply to every payload

The ledger stores a projection, never a serialization of OLD, NEW, a request
body, a provider response, or a database error. The following are forbidden in
changed_fields, before_values, after_values, metadata, labels, logs emitted by
the writer, and API responses:

- a raw credential, token, API key, password, ciphertext, private key,
  certificate, recovery value, provider response, bank number, government ID,
  invitation token, or validation error;
- a partial secret, including a prefix, suffix, last-four value, mask,
  truncation, base64 representation, encrypted representation, or any
  reversible encoding;
- a low-entropy fragment that could aid matching, such as a short provider
  identifier copied from a secret;
- an unsalted digest or hash of a sensitive value, including a generic
  cryptographic digest;
- raw nested configuration from custom_settings, repair_settings,
  shipping_providers, feature_settings, premium_features, or equivalent JSON;
- a contact email, phone number, personal address, staff name, or raw
  permission document where the source classification calls for presence or a
  normalized projection instead.

These illustrative forbidden shapes contain placeholders, not data:

~~~json
{ "credential": "<raw credential>" }
{ "credential_suffix": "<fragment>" }
{ "credential_hash": "<unsalted digest>" }
{ "provider_response": { "unreviewed": "payload" } }
~~~

Allowed redacted evidence is limited to a field name plus a semantic state:

~~~json
{ "present": true, "state": "configured" }
{ "present": true, "state": "rotated" }
{ "present": false, "state": "cleared" }
~~~

For a field whose value is individually classified as safe, the exact value is
allowed only in its named source-table projection below. The addition of a
field to a public request schema does not automatically make its value safe for
the immutable ledger.

## Payload approval process

The source classification is the only approved payload allowlist. To add,
remove, or change a projection:

1. Open a reviewed append-only migration; do not edit a released migration.
2. Name every affected source column in exactly one classification.
3. Make an unclassified-column mutation fail closed in the SQL contract and
   ensure the trigger fires for every governed column change; do not rely on an
   `UPDATE OF` list that lets an unknown-only mutation bypass the guard.
4. Add positive and negative SQL regressions covering create, update, clear,
   delete/cascade where applicable, no-op, and rollback.
5. Add a leak test that scans the serialized complete audit row for raw,
   partial, masked, encoded, and unsalted-hash forms of sensitive test inputs.
6. Obtain security review of the exact projection, not merely the route that
   caused the write.
7. Update this governance document in the same pull request.

No developer may approve a payload expansion merely because the audit reader is
owner-only. Immutable retention makes a mistake durable.

## Read access and approvals

The current audited read surface is GET /api/audit-events and the underlying
list_merchant_audit_events_v1 RPC.

- The request authenticates before parsing filters or resolving a merchant.
- The selected merchant must match the authenticated user's server-resolved
  owner context.
- Staff are forbidden, even if their settings permissions are broad.
- The RPC enforces the same owner relation again in the database.
- Results are private and no-store; filters, cursor pairs, and response
  projection are strict and bounded.
- Labels that look like email addresses are suppressed by the route.

Expansion beyond an owner requires an explicit approval with all of the
following: merchant authorization, least-privilege role scope, a database
policy/RPC change, route authorization, regression tests for denial and
cross-tenant reads, privacy review of the returned fields, and a security
review. Support or platform investigation must use a time-bounded,
ticketed break-glass process outside this endpoint; it must not gain a hidden
unscoped API parameter.

## Deletion, retention, and tombstones

The deployed Phase 1 ledger has no automatic retention purge. The following is
a proposal, not an implemented legal-retention policy:

- Retain the minimum canonical event envelope for seven years from occurred_at
  for payment configuration, credential lifecycle, staff access, and merchant
  configuration events, subject to legal and data-owner approval.
- Keep source-table deletion evidence as immutable snapshots. Do not UPDATE or
  DELETE historical audit rows to make a source row disappear.
- If a source requires deletion evidence beyond the current actions, append a
  new safe tombstone event; never mutate a prior event. The tombstone may
  identify the deleted resource and reason code but may not recreate deleted
  values or secrets.
- Any future archival or purge design requires a separate migration, explicit
  retention owner, backup/restore behavior, legal review, count/hash receipt,
  and proof that only events past the approved horizon are affected.

Account deletion or merchant deletion does not grant a broad audit-row delete.
The current no-source-FK design lets events survive source deletion. A future
privacy/legal workflow must resolve retention law before changing that property.

## Committed-state-only rule

The ledger is evidence of committed database state:

- source triggers run AFTER the row mutation;
- event insertion occurs in the same database transaction;
- any trigger, writer, or source failure rolls back the source mutation and
  its audit evidence together;
- an application rollback leaves neither a durable source change nor a durable
  audit event;
- an event is not an external side effect, queue message, or best-effort log.

Do not emit a companion audit event from client code before the database
transaction commits. If a later phase needs an external notification, it must
derive from committed evidence through a separately reviewed outbox design.

## Incident procedure: unexpected merchant identity change

1. Preserve the event ID, merchant ID, resource ID, occurred_at,
   database_transaction_id, action, actor fields, source, correlation ID, and
   request ID. Do not edit or delete the event.
2. Determine the affected domain. A merchant identity change can be paired with
   a merchant configuration event under the same database_transaction_id.
3. Contain the account according to the risk: suspend the affected staff
   membership, revoke active sessions, restrict configuration writes, or
   temporarily unpublish the storefront. Use an approved operational path; do
   not perform ad hoc direct ledger writes.
4. Verify the actor/source against trusted authentication, database, and
   request records. Treat service or database attribution as an escalation
   requiring review of the authorized writer path and change history.
5. Compare the safe before/after projection with the current source row using
   an authorized operational read. Do not copy raw sensitive source values into
   tickets, chat, or a new audit metadata field.
6. Restore or correct source state through a normal governed mutation so the
   remediation has its own committed audit event. Record the incident reference
   only in the approved incident system, not in arbitrary audit metadata.
7. Review adjacent events by database_transaction_id and the bounded owner
   audit reader. Escalate cross-tenant, direct-write, actorless-attempt, or
   redaction concerns as security incidents.
8. Document root cause, containment, customer/merchant notification decision,
   and follow-up work. Preserve the original event as evidence.

## Required release evidence

A release that changes a canonical audit migration, trigger, reader, source
classification, or payload projection must supply:

- append-only migration verification and replay-manifest SHA verification;
- static review for empty search_path, fully qualified security-definer
  references, function owner, revoked trigger-wrapper EXECUTE, forced RLS,
  direct ledger write revokes, and immutable UPDATE/DELETE denial;
- all six canonical SQL regression fixtures in chronological PostgreSQL 17
  replay with every registered pending source;
- corresponding TypeScript migration contracts and audit API/schema tests with
  mocked clients and no live sockets;
- a serialized-row leak scan covering raw values, suffixes, masks, encodings,
  and unsalted hashes for every newly sensitive field;
- lint, typecheck, and a full test receipt. An unrelated pre-existing failure
  must be explicitly identified by exact test and evidence rather than treated
  as a passing gate;
- independent security review and CodeRabbit review. If a review tool is
  externally blocked, record the exact command/error and perform an
  independent read-only review before commit.

Before deploy, the exact migration file hashes must match the pending-source
manifest and the replay receipt must identify the exact commit. A green focused
test does not waive the full replay, immutability, or redaction gates.

## Follow-on phases

Phase 1 intentionally does not claim whole-system audit coverage. Follow-on
work must be separately designed and reviewed for:

1. payouts, payment execution, wallet/VTU, negotiated-price overrides, and
   external provider outcomes;
2. account deletion and recovery-code flows, including retention and actor
   behavior;
3. an audited service-role write inventory with a classification for every
   sensitive mutation path;
4. bounded support/admin break-glass reads and an owner-facing activity UI;
5. approved retention/archive execution, tombstone policy, and recovery drills;
6. a controlled system/migration actor path, correlation propagation, and any
   future external audit export or SIEM integration.

Each follow-on must preserve the same core rule: record safe, attributable,
committed evidence without turning the immutable ledger into a credential,
contact-data, or raw-request archive.
